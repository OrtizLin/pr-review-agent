# PR Review Agent

A developer-productivity AI agent: given a pull request diff, it runs real
tools first (lint, tests, codebase search, guideline retrieval), then drafts
a structured code review. A human approves before anything is merged.

This is portfolio project 1 for a Senior AI Agent Development Engineer role.
It is built to evidence, not just claim:

- AI agents and LLM applications
- Prompt engineering (versioned prompts in `pr_review_agent/prompts.py`)
- RAG over team guidelines and past review notes
- Tool calling (lint, tests, search, diff)
- AI workflow automation (CLI + GitHub Actions)
- Developer productivity tooling (a code assistant, not a consumer chatbot)
- Solid software practice: tests, CI, structured output, human-in-the-loop

## What it does

1. Collect the diff (`git diff base...head`, or `--sample` for a demo diff).
2. Run tools: a linter if available, the test suite if available, and a
   keyword search over the changed files.
3. Retrieve the relevant team guidelines (`docs/guidelines.md`).
4. Draft findings with file, line, severity, evidence, and a suggested fix.
5. Validate findings: every finding must point at a file actually in the
   diff. Findings that fail validation are dropped, not hallucinated.
6. Render a Markdown report and a machine-readable JSON report.
7. Stop before merge. A human reviews the report and decides.

## Quick start (no API key needed)

```bash
cd pr-review-agent
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m pr_review_agent.cli --sample --dry-run
python -m pytest -q
```

`--dry-run` uses a deterministic rule-based reviewer, so the whole pipeline
runs offline and is testable. The real LLM path is implemented in
`pr_review_agent/llm.py` (OpenAI-compatible, no vendor SDK) and uses the
same validated output schema. Without a key it errors clearly instead of
faking a review. Do not commit API keys; see `.env.example`.

```bash
# Set the key in your shell only, never in chat or a committed file:
export LLM_API_KEY="..."
export LLM_MODEL="gpt-4o-mini"  # or a model you actually have access to
python -m pr_review_agent.cli --sample --no-dry-run
```

## Layout

```
pr_review_agent/
  cli.py        # entry point, human-in-the-loop boundary
  agent.py      # agent loop: tools -> draft -> validate -> report
  git_tools.py  # diff parsing
  tools.py      # lint, tests, search, guideline retrieval (RAG stub)
  prompts.py    # versioned prompts
  report.py     # Markdown + JSON rendering
  config.py     # settings

  guidelines.md # team rules the agent retrieves from
  architecture.md
examples/
  sample_repo/  # small fixture with intentional issues
  sample_diff.diff
eval/
  cases.json    # evaluation cases (expand to 20-30)
  run_eval.py   # scores: issue found? file real? severity sane?
tests/          # pytest, no network
.github/workflows/ci.yml
```

## Evaluation, not just a demo

`eval/cases.json` has 24 cases (generated by `eval/generate_cases.py`).
Run:

```bash
python eval/run_eval.py
python eval/compare_retrieval.py
```

Score a case as a pass only when the expected issue is found in the right
file, severities match where specified, and no finding points at a file
outside the diff. Add cases for every new rule or prompt change; do not
tune prompts on the eval set and then report the same set as if it were
held out.

Retrieval comparison (4 queries, 5 guideline lines): the old
keyword/full-file method returned the whole file every time. TF-IDF
retrieval in `pr_review_agent/retrieval.py` gets top-1 correct on 4/4
queries; see `eval/retrieval_comparison.md`. A model-embedding
retriever is now implemented in the same shape
(`EmbeddingRetriever`, `pr_review_agent/embeddings.py`, OpenAI-compatible
`/embeddings`, Gemini preset `gemini-embedding-001` — not the retired
`text-embedding-004`, which returns HTTP 404 on the v1beta
OpenAI-compatible path). Verified 2026-11-05 against a real model:
TF-IDF scored 4/4 on the original queries and 2/5 on the paraphrase
queries; embedding (`gemini-embedding-001`) scored 4/4 and 5/5.
Under the pre-stated rule (beat TF-IDF on paraphrases without
losing on originals), embedding is now the default when an
embedding key is set, and TF-IDF is the offline fallback when no
key is set; the retriever actually used is stated in the output.
Set `RETRIEVER=tfidf` to force TF-IDF, or `RETRIEVER=embedding`
to force embedding (which errors clearly with no key).

## Evaluation: development set vs held-out set

- Development set: `eval/run_eval.py` scores 24/24 cases in
  `eval/cases.json`. These cases were used while building the tool.
- Held-out set: `eval/run_heldout.py` scores 12/12 cases in
  `eval/heldout_cases.json`. These cases were written afterwards,
  with different scenarios (including needles that appear only in
  context lines or removed lines, which must NOT be flagged), and
  were not used to tune rules or prompts. Report the two scores
  separately; do not merge the held-out cases into the development
  set, and do not change code to make a failing held-out case pass
  without saying so, or the held-out score stops meaning anything.

## PR review comment action

`.github/workflows/pr-review.yml` runs on pull requests: it runs
the dry-run reviewer on the PR diff (base...head) and posts the
Markdown report as a PR comment with `gh pr comment`. Permissions
are only `contents: read` and `pull-requests: write`. It does not
merge, approve, request changes, or modify code. V1 posts a new
comment on every run; it does not update a previous comment.
The workflow file is YAML-valid and the CLI command it runs was
simulated locally on a test repo (2 findings, correct files and
lines), but the action itself has NOT yet been verified by a real
test PR on GitHub — that step still needs a push and a test PR.

## What is intentionally not here yet

- No auto-merge, no auto-push, no direct write to a repo. The agent
  reports; a human decides.
- No model vendor is hard-coded. The LLM boundary is one function.
